# Outreach

Outreach should be maintainer-to-maintainer, specific, and useful. The goal is to start technical conversations with people whose projects have a direct reason to use repository metadata.

## Targeting

Prioritize public projects that already work with:

- repository catalogs;
- developer portals;
- GitHub metadata;
- open-source analytics;
- RAG/retrieval systems;
- language or topic indexes;
- research datasets;
- developer tooling.

## Message pattern

1. Name the relevant project or workflow.
2. Identify the specific friction RepoSource may reduce.
3. Link to the exact useful artifact: dataset, schema, example, or research note.
4. Ask one technical question.
5. Do not imply endorsement, partnership, or existing usage.

## Example

> I maintain RepoSource Registry, an open snapshot of GitHub repository metadata with a published schema and focused partitions. I noticed your project builds [specific repository-discovery workflow]. The language/category partitions may remove some repeated collection work. If useful, I would value feedback on whether the current schema fits that workflow.

## Channel discipline

Use the community's normal contribution or discussion mechanism. Suitable channels may include GitHub, relevant technical forums, research communities, LinkedIn, Dev.to, Reddit, and Hacker News when the material is genuinely relevant.

Do not use bulk messaging, automated comments, fabricated engagement, or misleading claims.

## Success signals

A useful conversation produces a test, issue, pull request, downstream integration, citation, example, or concrete feedback. Silence is not a failure of the product; it is evidence that the target or message may be wrong.
