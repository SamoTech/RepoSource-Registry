# Growth strategy

RepoSource Registry should grow through useful downstream work, not manufactured attention.

## Adoption funnel

**Discover → understand → use → return → reference/star → contribute → cite → sponsor → buy services**

Each stage depends on the previous one. A star without actual usage is not the objective.

## Acquisition channels

### GitHub

Improve the repository description, relevant topics, README clarity, releases, examples, issue quality, and contribution experience. Use repository topics and documentation to make the project's purpose easy to find.

### Technical search

Publish useful, non-duplicative documentation around real concepts represented by the dataset: GitHub repository dataset, repository metadata, repository discovery, open-source project discovery, and machine-readable GitHub data.

### Developer communities

Share concrete use cases rather than generic project announcements. Appropriate channels may include technical communities, Reddit, Hacker News, Dev.to, LinkedIn, developer newsletters, and open-source forums when the content is genuinely relevant to the audience.

### AI and data ecosystem

Make the canonical data path, schema, provenance, limitations, and examples easy for developers and automated systems to understand. Encourage downstream projects to reference the snapshot and verify current facts upstream.

### Research

Create reproducible examples and invite legitimate research use. External citations and downstream studies are stronger evidence of value than raw traffic.

## What to measure

Prioritize:

- real downstream projects using the data;
- forks and meaningful contributions;
- external references and citations;
- repeat use of the dataset;
- useful data-quality reports;
- integrations built by others;
- sponsorship from users or organizations with a demonstrated reason to support the infrastructure;
- paid service engagements that arise from actual implementation needs.

Stars are useful as a discovery signal but are not the product goal.

## Community flywheel

Useful dataset → developer discovers it → developer uses it → developer returns or references it → issues and contributions improve it → data quality improves → more downstream tools and research use it → companies encounter real ecosystem value → sponsorship and services become rational.

## Anti-patterns

Do not buy stars, create fake issues, manufacture testimonials, mass-post links, scrape personal contact data, create artificial contributor activity, keyword-stuff documentation, or manipulate search and ranking systems.

## Validation loop

Before adding a growth feature, answer:

1. Who needs this?
2. What evidence shows the need?
3. What user behavior would demonstrate usefulness?
4. What maintenance cost does it introduce?
5. Does it improve the open project even if nobody pays?
